# VivagoAgent CLI Marketplace 历史控制设计

## 状态

- 日期：2026-08-20
- 状态：个人 Dev 通道已实测通过；公司 Beta 工作流代码已接入，仓库规则未满足上线要求
- 适用通道：个人 GitHub `dev-marketplace`、公司 GitHub `marketplace`

## 背景

VivagoAgent CLI 的安装包为自包含插件，当前同时内置 macOS、Linux、Windows 的 ARM64 和 x64
二进制。当前 Marketplace 快照中的六份二进制约为 40 MiB，用户检出后的仓库和 Git 元数据约为
55 MiB。该体积主要来自当前可安装版本，不是 `main` 源码历史膨胀。

改造前的发布流水线以普通快进提交持续更新 `dev-marketplace` 和 `marketplace`。如果每个版本都保留
一套新的多平台二进制，安装分支的可达历史会随版本线性增长，完整克隆、插件安装和更新最终会受
影响。

## 目标

- 保持插件内置六平台二进制，用户安装方式和运行方式不变；
- 让安装分支始终只包含当前发布快照，不随发布次数线性增长；
- 保留 Tag、GitHub Release、checksum、SBOM 和构建证明的不可变性；
- 使用精确租约避免并发或过期流水线覆盖更新后的安装通道；
- 个人 Dev 和公司 Beta 使用同一套快照发布机制，仅环境、版本和仓库身份不同。

## 不在本次范围

- 不使用 Git LFS；
- 不改为首次运行时按平台下载二进制；
- 不减少当前单个 Marketplace 快照的体积；
- 不修改 CLI、登录、VivagoAgent API 或用户数据；
- 不改变现有 Beta 版本递增和安全替代版本策略。

## 方案比较

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 每次发布创建无父提交的快照，并用精确租约更新分支 | 分支体积长期稳定；安装包不变；规则明确 | 安装分支需要允许发布机器人受控改写 | 采用 |
| 累积到阈值后定期压缩历史 | 强制更新次数少 | 体积仍阶段性增长；维护和阈值判断更复杂 | 不采用 |
| 将 Marketplace 移到独立仓库 | 源码仓库与二进制完全分离 | 新增仓库、权限、地址迁移和运维成本 | 暂不采用 |
| Git LFS | Git 对象可能较小 | 宿主不保证执行 LFS smudge，可能安装到指针文件 | 不采用 |

## 发布模型

```text
main source SHA
  -> 完整测试和六平台构建
  -> 不可变 Tag + GitHub Release + 证明材料
  -> 无父提交的 Marketplace 快照
  -> force-with-lease 更新安装分支
```

职责边界如下：

| 载体 | 是否可改写 | 保存内容 |
|---|---|---|
| `main` | 否，按正常评审推进 | Go 源码、插件模板、测试和流水线 |
| Tag | 否 | 发布对应的准确源码 SHA |
| GitHub Release | 否 | 完整 Marketplace 压缩包、checksum、SBOM 和证明材料 |
| `dev-marketplace` / `marketplace` | 是，仅发布机器人受控更新 | 当前可安装版本的单提交快照 |

安装分支是可变的“当前版本指针”，不是版本档案。历史版本由不可变 Tag 和 Release 保存。

## 更新协议

发布流水线按以下顺序执行：

1. 完成现有测试、构建、Manifest 校验、环境扫描和发布审批。
2. 读取远端安装分支的准确 SHA，记为 `expected_old_sha`；分支不存在时记录为空。
3. 读取旧快照的 `BUILD_INFO.json`，验证候选版本单调递增；相同版本只有在内容完全一致时允许
   幂等退出，相同版本但内容不同必须失败。
4. 从已校验的 Marketplace 目录创建没有父提交的新快照提交，不继承 `main` 或旧安装分支历史。
5. 在推送前验证新提交只有一个可达提交、树内容完整、六份二进制及 checksum 匹配。
6. 使用精确租约更新远端：
   `--force-with-lease=refs/heads/<branch>:<expected_old_sha>`。分支不存在时只允许创建，不允许覆盖
   发布过程中由其他任务新建的分支。
7. 重新读取远端 SHA 和 `BUILD_INFO.json`，确认远端等于刚生成的候选快照。

不得使用不带准确旧 SHA 的 `--force`，也不得根据本地缓存猜测租约值。

## 失败和并发处理

- Release 创建失败：不更新安装分支。
- Release 已创建、安装分支更新失败：旧安装版本继续可用；相同源码 SHA 和版本可以重试剩余步骤。
- 两个任务并发发布：先成功者改变远端 SHA，后一个任务因租约不匹配失败，不能覆盖先成功者。
- 相同版本产生不同树：失败关闭，不能覆盖 Release 或安装分支。
- 发布后核验失败：停止发布并保留证据，不将安装分支强推回旧提交；修复后发布更高版本。

## 回滚关系

“受控改写快照分支”不改变产品的回滚原则。事故恢复仍使用更高版本号重新构建已验证的安全源码，
不会把 Tag、Release 或 Marketplace 指回一个有问题版本之前的旧提交。旧 Release 只用于兼容性验证、
审计和必要的人工指定版本恢复。

## 验证方案

先在个人 GitHub `dev-marketplace` 连续发布两个测试版本，再启用公司 Beta：

| 验证项 | 通过标准 |
|---|---|
| 快照历史 | 第二次发布后 `git rev-list --count` 仍为 `1` |
| 提交关系 | 快照提交没有父提交，也不包含 `main` 历史 |
| 体积 | 第二次发布后的可达 Blob 总量不超过单份候选包的 110% |
| 内容 | 六平台二进制、双宿主 Manifest、checksum、SBOM 和构建信息完整 |
| 幂等 | 同版本同内容重试成功且不产生新提交 |
| 冲突 | 使用过期 SHA 的发布被精确租约拒绝 |
| Codex | 隔离配置下完成全新安装、Marketplace 刷新和插件升级 |
| Claude Code | 自动化环境完成全新安装、Marketplace 更新和插件升级 |
| 旧版证据 | 上一版仍可从不可变 Release 获取并完成回滚验证 |

网络耗时受外部条件影响，不作为稳定的自动化断言；流水线使用提交数、可达对象体积和内容哈希作为
可重复的增长控制证据。

### 2026-08-20 个人通道实测

个人通道已完成 `0.3.0-dev.9` 和 `0.3.0-dev.10` 两次快照更新。切换前的 `dev.8` 安装分支有
6 个可达提交、约 252,698,711 字节可达 Blob；`dev.10` 更新后为 1 个无父提交、约
42,395,079 字节可达 Blob。当前快照的六平台包没有缩小，减少的是旧二进制历史。

| 检查项 | 结果 |
|---|---|
| `dev.9` 原始 Release | 保持不可变，资产摘要与恢复包一致 |
| `dev.9` 快照恢复 | 使用准确旧 SHA 的租约更新成功，快照无父提交 |
| `dev.10` 完整发布 | GitHub Actions 全绿，六平台 × 两宿主为 12/12 |
| `dev.10` 安装分支 | `parent_count=0`，`BUILD_INFO.json` 指向发布源码和 `channel=dev` |
| 上一版证据 | `dev.9` Prerelease 和资产仍可读取，没有被覆盖 |
| 公司 Beta | 工作流已改用共享脚本；没有触发新的生产 Beta |

`dev.9` 的第一次发布在 Marketplace 推送阶段失败，原因是临时仓库没有调用仓库的 Git remote 和
Actions 认证配置。修复后，快照仍在临时仓库创建，但从已认证的调用仓库执行精确 SHA 推送。
尝试用新源码重跑同一个 `dev.9` 时，Release 恢复校验又因源码 SHA 不一致主动拒绝；该保护保留，
没有通过放宽不可变规则绕过。最终使用 `dev.9` 原始 Release 包补齐安装分支，再由 `dev.10` 验证
完整自动发布。

## 权限和上线

- GitHub Actions 只能改写对应的安装分支，不能改写 `main`、Tag 或 Release；
- 公司仓库规则必须允许发布 Workflow 对 `marketplace` 使用受控强推，其他人员仍禁止直接推送；
- 若仓库规则无法限定 GitHub Actions 绕过者，发布先保持原方式，不降低整个仓库的保护等级；
- 个人通道验证和双宿主生命周期测试已经通过，公司 Beta 流水线已改用同一共享脚本；
- 2026-08-20 只读检查显示公司仓库没有 ruleset，`marketplace` 也没有分支保护；当前不能启用新的
  Beta 快照发布，需由仓库管理员先配置受控强推和人员写入限制；
- 该机制应在下一次 Dev/Beta 发布前完成，避免产生第二套可达二进制历史。

## 可量化完成标准

- Dev 和 Beta 发布代码已共用一个经过测试的快照更新脚本；
- 连续两次候选发布后安装分支均只有一个可达提交；
- 并发租约、幂等重试、同版本异内容、首次创建四类测试全部通过；
- 现有默认与 `prod` Go 测试、发布与分发测试、插件校验保持通过；
- README 安装和升级命令不变；
- 设计、发布文档和历史决策记录保持一致。

上述完成标准中的代码、个人通道和本地回归可以在本分支完成；公司规则和下一次 Beta 实际发布是
独立上线门禁，不能用个人仓库结果代替。
